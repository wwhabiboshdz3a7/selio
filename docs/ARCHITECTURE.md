# Architecture

## Vue d'ensemble

```
┌──────────────┐  HTTPS (cookie HttpOnly)   ┌──────────────┐   SQL (RLS)   ┌──────────────┐
│ apps/web     │ ─────────────────────────▶ │ apps/api     │ ────────────▶ │ PostgreSQL   │
│ vitrine+app  │  WebSocket (fenêtre de     │ Fastify      │               └──────▲───────┘
│ (Netlify)    │ ◀────────────────────────▶ │              │                      │ SQL (RLS)
└──────────────┘   connexion du Cloud)      │              │   Redis       ┌──────┴───────┐
┌──────────────┐  Bearer (jeton limité)     │              │ ────────────▶ │ apps/worker  │
│ apps/        │ ─────────────────────────▶ │              │ BullMQ et     │ tâches,      │
│ extension    │  lit la page visible       └──────┬───────┘ pub/sub Cloud │ Selio Cloud  │
└──────────────┘                                   │                       └──┬────────┬──┘
                                                   │ HTTP privé ou            │        │ Chromium neuf par action,
                                                   ▼ passerelle               │        ▼ profil temporaire
                                            ┌──────────────┐                  │   ┌──────────┐
                                            │ Ollama       │ ◀────────────────┘   │ vinted.* │
                                            └──────────────┘                      └──────────┘
```

- **Monorepo pnpm**, TypeScript partout, schémas Zod partagés (`packages/contracts`).
- **Séparation domaine / infrastructure / interface** : `packages/domain` ne dépend que de `contracts` ; `packages/core` orchestre les services sur `packages/db` ; `apps/api` n'est qu'une couche HTTP ; `apps/web` consomme une interface `DataClient` implémentée deux fois (démo locale, API).
- **Aucun processus permanent dans le navigateur** : les règles d'automatisation sont évaluées par le worker ; l'extension n'agit qu'à la demande sur la page ouverte.
- **Selio Cloud** (détails : CLOUD.md) : le worker ouvre un Chromium **sur notre machine, seulement pour agir** (une action ; bac à sable actif, environnement minimal, contexte sans enregistrement sur le disque, dossier de travail temporaire ; puis fermeture), au rythme humain et dans les plafonds de l'offre. Aucun processus permanent par compte. La fenêtre de connexion du client est filmée par capture d'écran CDP. Ses images et les entrées du client passent par Redis pub/sub (`cloud:screen:<id>`, `cloud:input:<id>`) entre le worker et l'API, puis par un WebSocket (ticket à usage unique) entre l'API et le navigateur du client. L'API ne lance jamais de navigateur.
- **Selio Radar** (détails : RADAR.md) : le worker passe **toutes les 30 s** (`radar.tick`) et lit les recherches dues (60 s en direct, 30 s pour 3 recherches prioritaires quand Radar Auto est ouvert, 1 h pour le simulateur, multiplié par le facteur de ralentissement). La lecture en direct passe par le compte Achat du client relié à Selio Cloud, dans le **même exécuteur Playwright** que les actions du Cloud : un Chromium neuf par page (`fetchPage`), puis fermeture. Lectures, achats de Radar Auto (`openBrowsing`), actions et fenêtres de connexion du Cloud prennent leurs navigateurs dans **un seul sémaphore partagé** (`BrowserSlots`, `CLOUD_MAX_BROWSERS`) et respectent le même **coupe-circuit de la machine** (`cloud_runtime`). Le cœur décide et enregistre (mesures, pause, alertes) ; `@selio/cloud` ne touche pas à la base. Les alertes partent du worker en **Web Push** (clés VAPID) vers les services de notification des navigateurs ; le navigateur du client ne reçoit que la clé publique. Le branchement dans l'API et le worker est livré en parallèle de ce document : état dans BUILD_STATUS.md.
- **Selio Track** (détails : TRACK.md) : statistiques seulement. Le worker passerait **toutes les 15 min** (`track.tick`) et lirait les empreintes dues, **une lecture par empreinte de critères** quel que soit le nombre d'organisations qui la suivent, relue toutes les 2 h (± 10 min, × facteur de ralentissement). Source par défaut : le simulateur ; derrière `TRACK_LIVE_ENABLED=false`, les pages **publiques** du catalogue lues sans session par le `RadarReader` de `@selio/cloud`, dans les mêmes créneaux de navigateurs et sous le plafond de pages de la machine (Radar prioritaire), avec la même conduite au premier signal (pause de Track, ralentissement, coupe-circuit de la machine). Le cœur n'enregistre que des agrégats et des références de prix ; les annonces ne sont reconnues que par une empreinte salée calculée dans la base.
- **Estimation des prix** (détails : PRIX.md) : service interne du cœur (`pricing.ts`) utilisé par Studio, Manager, Radar, Track et le panneau de l'extension. Deux moteurs : comparables (ventes de l'organisation et base de références partagée, affinés par le modèle 2 avec le cache d'embeddings de Radar) et modèle de prix `@selio/pricing` (gradient boosting quantile **sur le processeur**). Le worker ajouterait chaque nuit les ventes à la base de références (`pricing.references`) et entraînerait chaque semaine (`pricing.train`, dimanche 04:00 UTC, test sur le dernier mois) ; le modèle actif (`price_models`) est chargé par le worker et par l'API (rechargement horaire). Mon IA perso n'écrit que l'explication. Branchement API et worker livré en parallèle : état dans BUILD_STATUS.md.
- **Selio Studio** (détails : STUDIO.md) : préparation d'annonce façon Kavis dans le cœur (`studio.ts`). Les photos sont **réduites dans le navigateur** (côté long 1 024 px, JPEG ≈ 80, ≤ 1 Mo) et revérifiées par l'API dans leurs en-têtes ; le modèle 1 reçoit **6 photos au plus par appel** (tri par article), puis 2 pour l'étiquette et 3 pour le mètre ruban ; chaque valeur porte sa **provenance** (étiquette, ruban, base des références, vendeur) ou reste vide avec une question : rien n'est inventé. L'OCR d'essai (`OLLAMA_OCR_MODEL`, vide par défaut) n'intervient qu'en second recours. Les photos portées passent par une interface `WornPhotoProvider` (« noop » par défaut : aucun fournisseur choisi) et une file de nuit traitée par le worker (`studio.worn`, 22 h – 6 h) ; la précision des lectures est « à mesurer » (`pnpm studio:eval`, scripts/studio-eval).
- **Sauvegarde** (SAUVEGARDE.md) : `scripts/sauvegarde/` hors application. Chaque nuit, PostgreSQL et photos chiffrés avec age et copiés hors machine ; chaque mois, test de restauration.

## Modèle de données

Tables : `users`, `organizations`, `memberships`, `sessions`, `marketplace_connections`, `inventory_items`, `inventory_events`, `customers`, `conversations`, `messages`, `orders`, `shipments`, `automation_rules`, `automation_state`, `jobs`, `radar_searches`, `opportunities`, `purchase_requests`, `ai_requests`, `usage_events`, `subscriptions`, `payment_orders`, `invoices`, `payment_events`, `audit_logs`, `extension_tokens`, `rate_limits`, `password_resets`, `invites`, `invoice_counters`, `cloud_consents`, `cloud_accounts`, `cloud_actions`, `cloud_login_sessions`, `cloud_runtime`, `radar_reads`, `push_subscriptions`, `radar_alerts`, `embeddings_cache`, `track_filters`, `track_filter_reads`, `track_runtime`, `track_snapshots`, `track_scans`, `track_photo_searches`, `price_references`, `price_models`, `size_references`, `studio_preps`, `worn_photo_jobs`.

Points structurants :
- toute table métier porte `org_id` ; une politique RLS `org_id = app_current_org()` est **forcée** pour le rôle applicatif `selio_app` (non superuser) ;
- `orders.dedupe_key` unique par organisation (idempotence : référence externe, sinon article + client + jour) ;
- `jobs.dedupe_key` unique (règle + cible + jour local) ; `payment_events.id` unique (webhooks : `revolut:<order_id>:<event>`) ; `payment_orders.order_id` unique (une ligne par commande chez le fournisseur) ; `invoices.number` unique, `SEL-AAAA-000001` par une séquence SQL par année (`app_next_invoice_number`) ;
- `messages.external_ref`, `conversations.external_ref` uniques par organisation (ingestion idempotente) ;
- secrets de connexion en `bytea` chiffrés (clé hors base) ; jetons d'extension stockés hachés (SHA-256), préfixe public.
- `jobs.runs_in` vaut `server`, `browser` (remis à l'extension) ou `cloud` (exécuté par le worker dans Chromium) ; index partiel des tâches Cloud échues ;
- Selio Cloud (0011) : `cloud_accounts.connection_id` unique (un compte Cloud par compte Vinted, supprimé avec lui), session en `bytea` chiffrée (AES-256-GCM, données associées = identifiant du compte Cloud), verrou `running_since` ; `cloud_consents` (version, empreinte SHA-256 du texte, date, utilisateur) ; `cloud_actions` (journal de 90 jours, sans texte de message) ; `cloud_login_sessions` (empreinte du ticket seulement, `attached_at` : ticket à usage unique) ; RLS forcée sur ces quatre tables ; `cloud_runtime` (coupe-circuit de la machine, une ligne, aucune donnée d'organisation) ; `app_cloud_after_restore()` à lancer après toute restauration.
- Selio Radar (0012) : `radar_searches` porte la source (`demo` ou `cloud`), la priorité, le compte Achat lu, le facteur de ralentissement et les compteurs de pages et de blocages ; une affaire par référence Vinted et par organisation (index unique sur `observed->>'externalRef'`) ; une seule demande d'achat active par affaire (index unique partiel) ; `purchase_requests` garde le total réel, la référence de commande, l'article reporté dans Manager et la fin de l'attente 3-D Secure ; `radar_reads` (une ligne par lecture, 90 jours, base du taux de blocage et du ralentissement) ; `push_subscriptions` (adresse unique, liée à l'utilisateur et à une seule organisation) ; `radar_alerts` (file des notifications, une par affaire, sans donnée de vendeur) ; `embeddings_cache` (vecteurs du modèle 2 par organisation, modèle et empreinte du texte) ; RLS forcée sur ces quatre tables ; fonctions `SECURITY DEFINER` `app_radar_org_ids()` et `app_push_endpoint_release()`.

- Selio Track et estimation des prix (0013) : `track_filters` (unique par organisation et empreinte), `track_scans`, `track_photo_searches` (aucune colonne photo) sous RLS forcée ; tables partagées sans donnée d'organisation ni de personne : `track_snapshots` (agrégats par empreinte et par lecture), `price_references` (base de références, `dedupe_key` unique, organisation contributrice jamais renvoyée et supprimée avec elle) et `price_models` (modèles JSON, un seul actif) ; `track_filter_reads` (une ligne par empreinte) et `track_runtime` (sel des empreintes d'annonces, fenêtre partagée des blocages, facteur, pause de Track) **sans aucun droit pour `selio_app`**, atteintes par dix fonctions `SECURITY DEFINER` (`app_track_*`).
- Selio Studio (0014) : `size_references` (partagée, sans donnée d'organisation ni de personne, lecture seule pour `selio_app`, écriture par `app_size_reference_provide` et `app_size_reference_contribute` ; unique par marque, référence et taille normalisées), `studio_preps` (une ligne par article, RLS forcée, clés de stockage et rôles des photos, champs et mesures avec provenance, questions, `draft` → `validated`, purgée après 30 jours si jamais validée) et `worn_photo_jobs` (RLS forcée, file `scheduled_for`, clés de stockage vérifiées par la base, dépassement accepté daté et facture de rattachement) ; `extra_lines` sur `payment_orders` et `invoices` (lignes de dépassement comprises dans `amount_cents`).

- Négociation avancée et migration (0015) : `negotiation_limits` (historique des mesures des limites de Vinted ; `org_id` nul = mesure de l'équipe lisible par toutes les organisations ; `selio_app` lit et ajoute, sans modifier ni supprimer ; mesure globale par `app_negotiation_limits_record_global`), `migration_mappings` (correspondance « ancien → nouveau », brouillon puis appliquée ; texte collé ou fichier RGPD effacé 7 jours après par `app_migration_purge_raw_inputs`, captures jamais stockées), RLS forcée. Lots, situations, relance et seuils vivent dans les réglages JSON de l'organisation ; les règles `follow_up_24h` et `keyword_situation` dans `automation_rules`.

Migrations : `packages/db/migrations/*.sql`, runner `pnpm db:migrate` (table `schema_migrations`, verrou consultatif).

## Calculs financiers

- Montants : **centimes entiers** (`z.number().int()`), aucun flottant ; taux appliqués avec arrondi « demi vers l'infini ».
- CA = somme des prix de vente des commandes `paid`/`shipped`/`delivered`/`completed`, datées par création.
- Coût d'acquisition = prix d'achat + frais d'acquisition, **figé dans la commande** à la vente.
- Marge brute = vente − frais plateforme vendeur − port à charge vendeur − autres coûts − coût d'acquisition. Taux = marge / vente. Ce n'est pas un bénéfice net comptable.
- Prix plancher suggéré = max(acquisition + port + marge minimale absolue, (acquisition + port) / (1 − taux minimal − taux de frais)).

## Fonctions de vente (§5.14, « ce que Bleam n'a pas »)

Toutes pures dans `packages/domain`, servies par le cœur et affichées dans l'application ; aucune IA ne décide.

- **Prix conseillé par les ventes réelles** : estimation des prix (PRIX.md).
- **Marge de bout en bout** (`margin.ts`, `GET /api/analytics/margin`) : prix d'achat (reporté par Selio Radar, D37, ou saisi) + port et frais d'achat + emballage et autres coûts → revente. **Réalisée** une fois la vente payée (prix de vente, frais vendeur et port à sa charge déduits), **projetée** sinon (prix affiché). Marge brute opérationnelle en centimes, pas un bénéfice net. Carte « Marge de bout en bout » dans Analyses, par période.
- **Contrôle des photos et des mesures** (`photo-checks.ts`, `POST /api/items/:id/checks`, réponse `listingCheck` à l'enregistrement d'un article) : netteté par la variance du laplacien, calculée **dans le navigateur** sur une image réduite (512 px), seuil 100 à ajuster sur nos photos ; moins de 3 photos, aucune photo d'étiquette, mesures attendues pour la famille de la pièce (même table que Studio) moins celles qui portent une provenance ou figurent dans la description. Avertissements **jamais bloquants**, aucune mesure inventée.
- **Lots intelligents** (`bundles.ts`, Stock › Lots) : propositions par règles explicites (même acheteur, même marque et taille, articles anciens), remise bornée par le plancher de lot de la négociation ; rien n'est envoyé.
- **Seuils de déclaration** (`thresholds.ts`, `GET /api/analytics/thresholds`) : ventes et montant encaissé de l'année civile (commandes comptées dans le CA) face aux seuils de transmission des plateformes à l'administration (30 ventes ou 2 000 € depuis 2026, `settings.thresholds`, paramétrables) ; alerte à partir de 80 % de l'un d'eux, « atteint » dès qu'un seuil l'est. **Information factuelle seulement** : le texte (`THRESHOLD_DISCLAIMER`) dit que ce n'est pas un conseil fiscal et renvoie vers l'administration ; un test refuse toute tournure de conseil.

## Politique de négociation (déterministe)

`evaluateOffer` → `accept | counter | decline | escalate | hold` avec les raisons :
1. hors plage horaire → `hold` ; limite par acheteur atteinte → `escalate` ;
2. offre ≥ prix affiché → `accept` ; offre ≥ plancher et remise ≤ remise max → `accept` ;
3. sinon contre-proposition = max(plancher, prix − remise max, prix − pas × (tour + 1)) ; au-delà du nombre de tours → `escalate`.

Négociation avancée (détails : NEGOCIATION.md) :
- **lots** : `evaluateBundleOffer` réutilise `evaluateOffer` sur le lot entier ; plancher du lot = max(somme des planchers réels, total affiché × (1 − remise maximale de lot)), jamais sous la somme des planchers ; prix retenu réparti au prorata des prix affichés, en centimes exacts ;
- **situations par mots-clés** : comparaison de mots entiers normalisés ; seule surcharge possible `escalate` (transmettre au vendeur) ;
- **limites de Vinted** (`applyLimitsToDecision`, appliquée après la politique et la situation) : contre-offres au-delà de la limite → `escalate`, message trop rapproché → `hold` ; valeurs prudentes « à mesurer » tant qu'aucune mesure datée n'existe (mesure de l'organisation, sinon de l'équipe, sinon réglages) ;
- **relance après 24 h** (`decideFollowUp`) : une par conversation, aux heures actives, mode selon l'offre (`none`, brouillon en Pro, Selio Cloud en Agence).

L'IA reçoit la décision et rédige ; sa sortie est validée par schéma puis par politique (intention cohérente, prix identique au prix imposé, aucun lien/HTML, aucune fuite du prix d'achat ou du plancher, aucun écho d'injection). En production, une défaillance IA remonte une erreur explicite ; le repli sur gabarit n'existe qu'en démonstration ou pour les automatisations (qui continuent sans IA).

## Flux clés

- **Envoi d'un message** : brouillon → `pending` → connecteur (`sendMessage` idempotent par identifiant) → `sent` (avec `simulated` si démo) ou `failed` avec raison. Jamais `sent` avant confirmation.
- **Commande** : création idempotente ; transitions contrôlées ; statut d'article dérivé (réservé / vendu / remis en vente).
- **Automatisation** : règle → garde-fous (`gateRule` : pause globale, activée, horaires, limites jour/acheteur, délai minimal) → job (`awaiting_approval` par défaut) → exécution serveur ou remise à l'extension (`runsIn = browser`), nouvelles tentatives exponentielles bornées.
- **Offre d'un acheteur (règle `auto_negotiate`)** : dernier message de l'acheteur → offre de lot reconnue (`detectBundleOffer`, articles des conversations ouvertes du même acheteur) → `evaluateBundleOffer`, sinon `evaluateOffer` → situation « transmettre au vendeur » (`applySituationOverride`) → limites de Vinted (`applyLimitsToDecision`) → gabarit (`bundleMessage` ou formule D20) → tâche ; `hold` et `escalate` ne partent pas.
- **Relance après 24 h (règle `follow_up_24h`)** : passage des automatisations (5 min) → `decideFollowUp` (quota `followUp24h` de l'offre, clé `follow_up_24h:<conversation>`) → Pro : brouillon dans Messages + tâche `awaiting_approval` (envoyée ou annulée depuis Messages) ; Agence avec compte actif dans le Cloud : tâche `runs_in = cloud` (action légère `follow_up`) ; sinon brouillon.
- **Situation par mots-clés (règle `keyword_situation`)** : dernier message de l'acheteur → `matchSituation` → gabarit (tâche normale) ou transmission / rédaction par mon IA perso (tâche à valider) ; clé d'idempotence par message.
- **Migration des réglages** : texte collé, captures (modèle 1) ou fichier RGPD → `POST /api/migration/convert` ou `/file` → mon IA perso (sortie structurée, `validateMigrationMapping`) ou catalogue des équivalences sans IA → correspondance en brouillon (`migration_mappings`) → écran « ancien → nouveau » → `apply` : champs cochés seulement, revalidés par le schéma, relance migrée dans une règle `follow_up_no_reply` → purge de l'entrée brute à 7 jours (worker). Aucune requête vers l'outil d'origine.
- **Extension** : content script (monde isolé, shadow DOM) → service worker (seul détenteur du jeton) → `/api/ext/*` (portées du jeton) → réponse d'affichage. Panneau « Comparables Selio » (Track, Pro et Agence) : sur une page article, le content script envoie les six champs de l'article (titre, marque, catégorie, taille, état, prix ; schéma strict) → le service worker les revalide et appelle `POST /api/ext/comparables` → estimation sans explication (fourchette, stratégies, délai, comparables, méthode, position du prix affiché) revalidée puis affichée en texte ; hors ligne, non relié et « Track est compris à partir de Pro » ont leur état ; rien n'est enregistré.
- **Selio Track** : `track.tick` (worker, toutes les 15 min) → empreintes dues (`planTrackReads`), une à la fois dans les plafonds de pages (Track, puis machine) → `runTrackRead` : garde-fous (lecture en direct ouverte, pause de Track, coupe-circuit) → prise de l'empreinte (bail de 10 min) → simulateur, ou page publique lue par `CloudTrackReader` (sans session, champs du vendeur vidés) → annonces revalidées, empreintes salées par la base → disparitions (annonce qui aurait dû rester sur la page), instantané, références (`listed`, `gone` au prix final estimé) → prochaine lecture. Premier signal de Vinted : pause de Track écrite d'abord, facteur partagé doublé, coupe-circuit de la machine pour un blocage ou un « trop de requêtes », fin du passage, rien n'est retenté.
- **Estimation d'un prix** : caractéristiques → comparables (ventes de l'organisation et références, même catégorie ; similarité des titres par le modèle 2 avec cache, sinon marque et catégorie, sinon marque) → prédiction du modèle actif (P25 / P50 / P75, délai) → combinaison (poids des comparables 0,8 × min(1, n / 12)) → trois stratégies arrondies à x,90 → explication facultative par mon IA perso, écartée si elle cite un montant ou un chiffre absent des faits. Ni comparable ni modèle : « Pas assez de références », aucun prix.
- **Selio Cloud** : règle « répondre » ou « relancer » sur un compte actif dans le Cloud → tâche `runs_in = cloud` → passage du worker chaque minute (`runDueCloudJobs`) : au plus une action par compte, garde-fous (arrêt global, coupe-circuit, accord de la version courante, offre, plafond de comptes, compte actif, session, niveau léger, heures actives 8 h – 23 h, plafond du jour `automationActionsPerDay`, 12 par heure, 3 à 7 min entre deux actions) → verrou du compte, **relecture sous verrou** (arrêt global, coupe-circuit, accord, offre, plafond de comptes) et prise unique de la tâche → Chromium hors transaction → journal `cloud_actions`, compteur `cloud.action` (seulement si le navigateur a été lancé), session refiltrée et rechiffrée si elle n'a pas changé entre-temps. CAPTCHA, avertissement, blocage ou « trop de requêtes » → pause du compte écrite d'abord, email, rien n'est retenté ; « trop de requêtes » ou blocage → coupe-circuit de la machine ; session refusée → connexion à refaire ; aucun navigateur libre → tâche remise en file sans rien compter.
- **Selio Radar** : `radar.tick` (worker, toutes les 30 s) → `planReads` (fonction pure : recherches dues, prioritaires d'abord) → `runSearch` par recherche due, dans les plafonds de pages par minute (organisation, puis machine) → garde-fous (arrêt global, coupe-circuit, rythme, compte Achat relié à un compte Cloud actif avec session, accord Cloud) → verrou du compte Cloud, session déchiffrée → Chromium hors transaction (`fetchPage`, page catalogue lue puis refermée ; aucun créneau libre : rien n'est lu ni compté) → annonces revalidées, dédoublonnées (référence Vinted, sinon titre et prix) → revente estimée hors transaction (embeddings du modèle 2 avec cache, sinon marque et catégorie) → note, affaire, alerte en file (note ≥ 75, heures calmes), ligne `radar_reads`, facteur de ralentissement. CAPTCHA, avertissement, blocage ou « trop de requêtes » → pause du compte Cloud écrite d'abord (`cloud.pauseFromSystem`), coupe-circuit de la machine pour « trop de requêtes » et blocage, email et notification, mesure « bloquée », rien n'est retenté. `alerts.send` (chaque minute) envoie les alertes échues en Web Push.
- **Radar Auto** (fermé par défaut) : `radar.auto` (worker, toutes les 30 s, seulement si `RADAR_AUTO_ENABLED`) → verrous (serveur, organisations de l'équipe, réglage de l'organisation, compte Achat dans le Cloud, accord) → affaires nouvelles de la mieux notée à la moins bien notée (seuil, prix maximum par article, plafond du jour, contrôles) → réservation (index unique) → au plus un achat par le navigateur et par passage (`openBrowsing` : annonce, « Acheter », porte-monnaie Vinted, total relu ; essai à blanc arrêté avant le paiement tant que `RADAR_REAL_PURCHASE` est fermé) → issue enregistrée, prix d'achat reporté dans Manager. Validation 3-D Secure : navigateur tenu ouvert (`CLOUD_3DS_TIMEOUT_MS`), notification, le client valide dans sa banque, reprise mise en file par l'API (`selio-radar`) et relue par le worker sans rien saisir ; délai passé : abandon et alerte, rien n'est racheté.
- **Selio Studio (préparation)** : photos réduites par le navigateur → `POST /api/studio/prepare` (toutes les photos vérifiées dans leurs en-têtes avant tout appel ; 413 / 422 sinon) → tri par le modèle 1 en lots de 6 (`planPhotoBatches`, `mergeSortBatches`, rôle du vendeur prioritaire) → par article : étiquette (2 photos, `readLabel`, OCR d'essai en second recours), mètre ruban (3 photos, `readMeasurements`, aucune mesure sans ruban visible), base des références par la marque et la référence lues → fusion avec provenance (`mergeFields`) et questions au vendeur → une ligne `studio_preps` par article, une requête IA comptée → `POST /api/studio/preps/:id/validate` (réponses = provenance `seller`, partage anonyme des mesures vers `size_references`) → `POST /api/studio/generate` avec `prepId` (marque, taille, matière et mesures imposées, rien n'est relu, un `studio.listing`).
- **Photos portées** : `POST /api/studio/worn` (quota `studio.worn_photo`, dépassement seulement si `WORN_OVERAGE_ENABLED` et accord explicite) → file pour le prochain créneau de nuit → `studio.worn` (worker, toutes les 10 min, dans la fenêtre seulement) → `WornPhotoProvider` (« noop » : refus propre, quota rendu) → clé du résultat dans le stockage de l'organisation ; dépassement facturé au renouvellement (`billing.renew`, ligne `extra_lines`).
- **Paiement** : `POST /api/billing/checkout` crée la commande Revolut (pendant l'essai : capture manuelle d'un montant de vérification de 1 € ; ensuite : capture automatique du prix de l'offre) et renvoie son jeton public → le navigateur ouvre le formulaire Revolut (carte enregistrée « pour le marchand ») → le webhook signé confirme (`ORDER_AUTHORISED` sur une commande de vérification : carte retenue — celle de la tentative aboutie, lue sur la commande — et autorisation annulée ; `ORDER_COMPLETED` : période ouverte et facture, clôture atomique de la commande). `POST /api/billing/card` enregistre une nouvelle carte de la même façon (1 € autorisé puis annulé) ; en retard de paiement, le débit est retenté dans l'heure. Le worker (`billing.renew`, toutes les heures) débite les renouvellements avec le moyen enregistré, relance à J+1 / J+3 / J+7 après un échec (une commande jamais présentée à la banque est remplacée sans compter d'échec ; une commande restée en traitement est annulée chez Revolut avant d'être comptée échouée) puis ramène à l'accès de base avec 30 jours de conservation, carte oubliée. Une période déjà payée n'est jamais écrasée (409 : changement d'offre ou de carte). Sans clé Revolut, aucune commande n'est créée et l'interface le dit.
