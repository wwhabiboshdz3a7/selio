# Sécurité

## Authentification et sessions
- Mots de passe hachés (scrypt, sel aléatoire), 10 caractères minimum.
- Sessions opaques (32 octets aléatoires) en base, cookie `HttpOnly`, `SameSite=Lax`, `Secure` obligatoire en production (`COOKIE_SECURE=true` imposé par la validation de configuration), expiration glissante 30 jours.
- Limitation de débit : globale par IP (300/min), connexion/inscription (compteur en base par IP + email), suggestions IA, envoi, création de jetons.

## Isolation multi-tenant
- Chaque requête métier ouvre une transaction `set local app.org_id = <org>` ; les tables métier ont une politique RLS **forcée** pour le rôle `selio_app` (non superuser, `NOBYPASSRLS`).
- Les contrôles d'autorisation applicatifs (`can(role, action)`) s'ajoutent à la RLS : propriétaire / administrateur / opérateur / lecture.
- Tests d'accès inter-organisations : `packages/db/src/db.test.ts` (RLS sans filtre applicatif) et `apps/api/test/api.test.ts` (404 sur ressources d'une autre organisation).

## Secrets
- Infrastructure : variables d'environnement validées au démarrage (Zod) ; `.env.example` avec placeholders uniquement ; aucun secret en Git.
- Par organisation : AES-256-GCM avec `SECRETS_ENCRYPTION_KEY` (32 octets base64, hors base) et AAD = identifiant de connexion.
- Jetons d'extension : `prefix.secret`, seul le hachage SHA-256 est stocké ; affiché une fois ; portées limitées ; expiration 90 jours ; révocation immédiate.
- Réponses API : jamais de hachage, de clé ni de secret ; `hasSecret` booléen uniquement.
- Journaux : en-têtes `cookie`, `authorization`, `x-health-token`, `set-cookie` masqués ; pas de corps de requête loggé.

## Entrées non fiables
- Validation stricte Zod sur toutes les entrées ; montants entiers ; tailles bornées.
- Messages acheteurs et contenus marketplace : nettoyage (caractères de contrôle, longueur), détection de motifs d'injection (journalisée), jamais interprétés comme instructions ; prompts IA balisés `<<<DONNÉES_NON_FIABLES>>>`.
- Sortie IA : schéma + politique (prix imposé, pas de lien/HTML, pas de fuite).
- Export CSV : neutralisation des formules (`=`, `+`, `-`, `@`).
- Interface : React échappe par défaut ; l'extension n'utilise que `textContent` dans un shadow DOM fermé.
- Fichiers : photos limitées à JPEG/PNG/WebP, 1,5 Mo, 12 par article côté application ; côté stockage, 5 Mo maximum, type et taille signés dans l'URL de téléversement (démo : data URL locale ; connecté : `/api/uploads`, voir docs/STOCKAGE.md et limites).

## En-têtes et réseau
- Netlify : CSP stricte (`script-src 'self'` plus les deux hôtes du formulaire de paiement Revolut, `frame-src` limité à ces mêmes hôtes, `frame-ancestors 'none'`), HSTS, nosniff, Referrer-Policy, Permissions-Policy. Même valeur dans `netlify.toml` et `deploy/netlify/_headers`.
- API : Helmet, CORS restreint aux origines configurées avec credentials, `frame-ancestors` via Helmet.
- Ollama n'est jamais exposé au navigateur : accès serveur → serveur via réseau privé ou passerelle authentifiée.

## Paiement (Revolut Merchant API)
- **Aucun numéro de carte ne transite par Selio** : la carte est saisie dans le formulaire Revolut Checkout (iframe et script servis par `merchant.revolut.com` ou le bac à sable), enregistrée « pour le marchand » chez Revolut. Selio ne stocke que des identifiants (`revolut_customer_id`, `payment_method_id`) et des montants ; les factures et l'interface disent « carte enregistrée » sans détail de carte.
- Le navigateur ne reçoit que le **jeton public** d'une commande (`POST /api/billing/checkout`), jamais la clé secrète ; le mode (bac à sable ou live) lui est transmis pour charger le bon widget. Le succès affiché par le formulaire n'est pas une confirmation : l'abonnement ne change qu'à la réception du **webhook** signé, et l'interface rafraîchit l'abonnement toutes les 5 s pendant une minute en le disant.
- Webhooks : corps brut, signature `Revolut-Signature` vérifiée en HMAC-SHA256 (`v1.<horodatage>.<corps>`, comparaison à temps constant, tolérance 5 minutes sur `Revolut-Request-Timestamp`, plusieurs signatures acceptées pendant une rotation du secret), idempotence par commande et événement (`payment_events`), commande inconnue ignorée, route limitée en débit, aucune session requise ni créée. Sans `REVOLUT_WEBHOOK_SECRET`, tout webhook est refusé (signalé au démarrage).
- Secrets : `REVOLUT_SECRET_KEY` (`sk_…`) et `REVOLUT_WEBHOOK_SECRET` (`wsk_…`) uniquement en variables d'environnement du serveur ; une clé qui ne commence pas par `sk_` est refusée ; les journaux du client Revolut ne contiennent ni clé, ni corps de requête, ni donnée de carte. Le mode live est refusé tant que `REVOLUT_LIVE_ALLOWED` n'est pas `true`.
- Débits à l'initiative du marchand (renouvellements, relances) : seulement avec un moyen de paiement enregistré « pour le marchand » et une commande ouverte par organisation à la fois (jamais deux débits pour une même échéance) ; après l'échéance puis J+1, J+3 et J+7 en échec, retour à l'accès de base avec conservation des données 30 jours. Toutes les actions de facturation exigent le rôle propriétaire (`billing.manage`) et sont journalisées dans l'audit sans montant de carte.

## Selio Cloud
Fonctionnement complet : CLOUD.md. Désactivé par défaut (`CLOUD_ENABLED=false`). État : BUILD_STATUS.md.
- **Aucun mot de passe Vinted** : le client se connecte lui-même dans la fenêtre sécurisée. Aucun type de donnée, aucune table, aucun journal ne porte de mot de passe ; l'IA ne voit jamais la fenêtre.
- **Session** : seuls les cookies des domaines de Vinted (**liste fermée** `VINTED_DOMAINS`, jamais une expression du type « vinted.<deux lettres> ») et le stockage local de leurs origines `https://` sont gardés, **sans les cookies de passage anti-robot** (`datadome`, `cf_clearance`…). Le filtre est appliqué avant tout stockage et testé contre les imitations de domaine (`vinted.lol`, `vinted.fr.evil.com`). Le réglage `vintedHost` d'une connexion est validé contre la même liste. Après une action, la session n'est réécrite que si c'est encore celle du début (compte relu sous verrou, date d'enregistrement inchangée). Chiffrement AES-256-GCM (`SecretBox`, clé `SECRETS_ENCRYPTION_KEY` hors base, données associées = identifiant du compte Cloud) dans `cloud_accounts.session_ciphertext`. Les lectures ordinaires ne renvoient jamais cette colonne ; l'API n'expose que « session enregistrée » et sa date. La session est effacée sur demande (un clic), à l'arrêt, à la déconnexion ou à la suppression du compte Vinted, quand Vinted ne la reconnaît plus, quand l'offre ne permet plus le Cloud (quelle qu'en soit la raison) ou pour les comptes au-delà du plafond de l'offre, et après toute restauration d'une sauvegarde (`app_cloud_after_restore()`).
- **Navigateur** : un Chromium neuf par action, **bac à sable actif** (jamais `--no-sandbox` ; vérifié au démarrage, Cloud désactivé sinon ; `CLOUD_CHROMIUM_SANDBOX=false` refusé en production), **environnement minimal en liste blanche** (aucune variable du worker : ni clé de chiffrement, ni base, ni paiement ; testé sur ce que Playwright transmet réellement), **contexte sans enregistrement** (cookies en mémoire, jamais dans un fichier), dossier de travail temporaire (0700) supprimé à la fin, en mémoire vive conseillé. Aucune option de furtivité, User-Agent non modifié, aucune résolution de CAPTCHA. Au premier signal de Vinted : pause (écrite d'abord, dans une transaction à part), email aux propriétaires, rien n'est retenté ; « trop de requêtes » ou blocage : coupe-circuit de toute la machine (60 min), alerte de l'opérateur dans le journal du worker.
- **Relais de la fenêtre de connexion** : ticket aléatoire montré une seule fois, seule son empreinte SHA-256 en base, valable 5 minutes (`CLOUD_LOGIN_TIMEOUT_MS`). Images (JPEG) et entrées du client circulent par WebSocket (API) puis Redis pub/sub (`cloud:screen:<id>`, `cloud:input:<id>`, rien n'est stocké). Les entrées sont validées par un schéma strict côté API, puis de nouveau côté worker. **Aucune frappe ni aucun clic n'est journalisé** ni cité dans une erreur. Côté API : origine vérifiée avant la mise à niveau WebSocket, **ticket à usage unique** (consommé par la première WebSocket ; verrou Redis en seconde barrière), fenêtre **annulée** dès que la WebSocket se ferme sans connexion réussie, au plus 5 ouvertures par quart d'heure et par utilisateur, 2 fenêtres ouvertes par organisation, `CLOUD_MAX_BROWSERS - 1` sur la machine. Le cadre principal de la fenêtre ne peut aller que sur une page https de Vinted ou d'un fournisseur de connexion, **redirections comprises** (chaque étape revérifiée, fenêtre fermée au moindre écart) ; aucune requête vers la machine ou le réseau local ; les fenêtres surgissantes sont fermées. Un CAPTCHA ou un autre signal de Vinted pendant la connexion ferme la fenêtre **sans enregistrer de session** et met le compte en pause.
- **Permissions** : `cloud.read` (tous les rôles : comptes, journal) ; `cloud.manage` (propriétaire et administrateur : accord, activation, pause, arrêt, suppression de session, fenêtre de connexion).
- **RLS** : `cloud_consents`, `cloud_accounts`, `cloud_actions`, `cloud_login_sessions` ont la politique `org_isolation` **forcée** pour `selio_app`, comme les autres tables d'organisation (`0011_cloud.sql`, testé : une organisation ne voit pas les comptes d'une autre). Deux fonctions `SECURITY DEFINER` limitées servent le worker hors contexte d'organisation. `app_find_cloud_login_session` retrouve une fenêtre par identifiant ou par empreinte de ticket. `app_cloud_org_ids` liste les organisations qui ont des comptes Cloud, sans autre donnée. `cloud_runtime` (coupe-circuit, une ligne) n'a aucune donnée d'organisation ; `selio_app` peut seulement la lire et la modifier. `app_cloud_after_restore()` n'est exécutable que par le propriétaire de la base.
- **Accord** : enregistré avec la version, l'empreinte SHA-256 du texte, la date, l'utilisateur et l'adresse IP. Sans accord valide pour la version courante, aucune activation ni aucune action.
- **Journal et audit** : `cloud_actions` (90 jours) ne contient ni le texte des messages ni aucun secret (clés du détail fermées) ; audit `cloud.*` pour l'accord, les comptes, les sessions, les fenêtres de connexion et les exports.

## Selio Radar et Radar Auto
Fonctionnement complet : RADAR.md. Radar Auto et l'achat réel sont fermés par défaut (`RADAR_AUTO_ENABLED=false`, `RADAR_REAL_PURCHASE=false`, D11). Les routes de l'API, les passages du worker et les pages web sont livrés en parallèle : état dans BUILD_STATUS.md.
- **Compte et session** : la lecture en direct et l'achat passent uniquement par le compte **Achat** du client relié à un compte Selio Cloud actif, avec l'accord Cloud valide (`checkLiveAccountTx`) ; jamais un compte Perso ni un compte de vente. Même session et mêmes règles que le Cloud (section ci-dessus) : aucun mot de passe, cookies limités aux domaines Vinted de la liste fermée et sans cookies anti-robot, déchiffrement avec les données associées du compte Cloud, session réécrite seulement si c'est encore celle du début, effacée si Vinted la refuse. Une lecture prend le verrou du compte Cloud : jamais en même temps qu'une action du Cloud sur ce compte.
- **Aucun contournement** : un CAPTCHA, un avertissement, un blocage ou un « trop de requêtes » arrête la lecture ou l'achat. La pause du compte est écrite d'abord, dans sa propre transaction (`cloud.pauseFromSystem`), puis le coupe-circuit de la machine (« trop de requêtes » ou blocage, 60 min, partagé avec le Cloud), puis l'email aux propriétaires. Rien n'est retenté. Le ralentissement automatique (l'intervalle double au-delà de 1 blocage pour 1 000 pages) est la seule réaction. Même lancement de Chromium que le Cloud : bac à sable, environnement en liste blanche, aucune option de furtivité, User-Agent d'origine, aucun proxy.
- **Pages lues = données non fiables** : le lecteur HTML des adaptateurs est borné (taille, nombre de nœuds, profondeur), sans exécution ni chargement ; chaque annonce est revalidée par un schéma strict côté cœur (adresses https d'un domaine Vinted de la liste fermée, photo https seulement, au plus 96 annonces par page). Radar n'ouvre que des pages catalogue ou annonce Vinted (`resolveRadarUrl`).
- **Navigateur d'achat** : la page tenue ouverte n'a **aucune méthode d'écriture** (aucun code bancaire ni aucune carte ne peut être saisi à la place du client) ; un clic n'est permis que sur une page Vinted, jamais sur la page de la banque ; elle ne navigue que vers une annonce ou un catalogue Vinted. Total relu avant de payer (au-delà du maximum : arrêt) ; tout échec après « Payer » est marqué « effets inconnus » et n'est jamais relancé. Achat réel seulement avec `RADAR_AUTO_ENABLED` **et** `RADAR_REAL_PURCHASE`, vérifiés par le cœur **et** par le navigateur (`realPurchaseAllowed`).
- **Verrous et droits** : `radar.read` (tous les rôles), `radar.write` et `purchase.simulate` (opérateur et au-dessus), `purchase.execute` (propriétaire : réglages de Radar Auto). L'activation de Radar Auto exige le verrou serveur (403 sinon) ; sa date et son auteur sont enregistrés par le serveur (`enabledAt`, `enabledBy`) et audités (`radar.settings_updated`). `RADAR_AUTO_ORG_IDS` limite Radar Auto aux organisations de l'équipe (obligatoire en production avec `RADAR_AUTO_ENABLED=true`).
- **Données des vendeurs** : pseudo, note, nombre d'avis et photo ne sont gardés que dans l'affaire, puis purgés (affaire écartée supprimée après 30 jours ; ces champs effacés des autres affaires 30 jours après leur création). **Jamais dans les journaux** : le worker ne journalise que des identifiants, des codes et des compteurs ; le message d'une exception (qui pourrait contenir une adresse ou un extrait de page) est remplacé par son type. Jamais dans la vue opérateur (`/api/admin/radar` : compteurs seulement), jamais dans les embeddings (titres et marques seulement).
- **Notifications (Web Push)** : contenu minimal `{ title, body, url }` validé par schéma (titre de l'annonce, prix, note, revente estimée), **jamais de pseudo, de note ni de photo du vendeur** ; `url` limité à un chemin relatif de l'application, revérifié par le service worker (`push-handler.js`) avant d'ouvrir quoi que ce soit. Durée de vie d'une heure chez le service de notification.
- **Abonnements push liés à l'utilisateur** : chaque abonnement porte l'utilisateur et l'organisation (`push_subscriptions`, RLS forcée) ; un utilisateur ne liste et ne retire que ses propres appareils ; une adresse d'abonnement est unique et ne sert qu'à une organisation (`app_push_endpoint_release` retire l'ancien abonnement quand l'appareil s'abonne ailleurs) ; les clés de l'abonnement (`p256dh`, `auth`) ne sont jamais renvoyées ni journalisées, l'adresse non plus. Côté API et worker (livrés en parallèle), seules les adresses des services de notification connus (Google, Mozilla, Microsoft, Apple), en https sur le port par défaut, sont acceptées : le serveur n'envoie jamais de requête ailleurs. 404 ou 410 : abonnement désactivé.
- **Clés VAPID** : `VAPID_PRIVATE_KEY` est un secret (`.env` du serveur seulement, jamais dans Git, Netlify ou le navigateur) ; seule la clé publique est servie au navigateur (`GET /api/push/config`). Une configuration à moitié remplie ou mal formée arrête le démarrage.
- **RLS** : `radar_reads`, `push_subscriptions`, `radar_alerts` et `embeddings_cache` ont la politique `org_isolation` forcée pour `selio_app` (`0012_radar.sql`, testé). Deux fonctions `SECURITY DEFINER` limitées : `app_radar_org_ids()` (organisations à passer par le worker, sans autre donnée) et `app_push_endpoint_release()` (rien n'est renvoyé).
- **Audit** : `radar.search_created` / `radar.search_deleted`, `radar.settings_updated`, `radar.push.subscribed`, `purchase.requested` / `confirmed` / `cancelled` / `auto` / `resumed` / `3ds_expired`, `cloud.account.paused` (origine `radar_read` ou `radar_purchase`), sans donnée de vendeur.

## Selio Track et estimation des prix

Détails : TRACK.md et PRIX.md. Les routes de l'API, le passage du worker et les pages web sont livrés en parallèle (état dans BUILD_STATUS.md) ; les garanties ci-dessous sont tenues par les contrats, la base et le cœur, déjà testés.

- **Statistiques seulement** : Track ne republie aucune annonce. Ses tables ne gardent que des agrégats (`track_snapshots` : nombres, prix médian, P25, P75, nouvelles, disparues, parts des marques) et des références de prix.
- **Références sans donnée personnelle** (`price_references`) : marque, catégorie, sous-catégorie, taille, matière, couleur, état, prix affiché et final, dates, nombre de photos, vues et favoris, source. Ni pseudo, ni profil, ni photo, ni titre libre, ni identifiant ou adresse d'annonce. Tenu par le code : `PRICE_REFERENCE_KEYS` (clés autorisées, testées), schémas stricts, champs personnels typés `never` dans `@selio/pricing`, ligne écartée (`personal_data`) et **fichier entier refusé** s'il a une colonne personnelle (`PersonalDataError`). Une vente convertie ne garde ni client, ni titre, ni identifiant de commande (clé = empreinte SHA-256 de l'organisation et de la commande) ; l'organisation contributrice (`contributor_org_id`) n'est jamais renvoyée et ses références sont **supprimées avec elle**. Moins de quasi-identifiants : dates **au jour** et nombre de photos **par tranches** pour Track et les ventes, base effacée après **24 mois**.
- **Ventes des clients** : versées dans la base **seulement avec l'accord de l'organisation** (`settings.pricing.shareSales`, désactivé par défaut, changement tracé `pricing.share_sales_enabled` / `_disabled`, retrait immédiat), retirées quand la commande est remboursée, annulée ou supprimée, et **jamais servies une à une** à une autre organisation : les comparables ne lisent que les sources `track` et `import`, et les agrégats (scans, flux des ventes, niches) excluent `source = 'sale'` d'une autre organisation. Elles ne servent qu'à l'entraînement agrégé du modèle (feuilles de 20 ventes au moins).
- **Annonces lues par Track** : reconnues d'une lecture à l'autre par une **empreinte salée calculée dans la base** (`app_track_ref_keys`) ; le sel est dans `track_runtime`, que le rôle `selio_app` ne peut ni lire ni modifier. Les références de Track sont écrites par la base (`app_track_store_references`) sous une clé dérivée avec un **second sel**, jamais rendue : la clé d'état qu'un appelant peut calculer pour une annonce n'est pas celle de sa référence. Limite : l'API et le worker partagent `selio_app`, donc `app_track_ref_keys` reste appelable par l'API ; un rôle worker distinct fermerait cette porte (à décider avec le déploiement). `track_filter_reads` (état par empreinte) et `track_runtime` (sels, fenêtre de blocages, pause) n'ont **aucun droit direct** : onze fonctions `SECURITY DEFINER` seulement, qui vérifient que l'organisation courante suit l'empreinte quand c'est pertinent. Avant d'atteindre le cœur, le lecteur du worker met à vide l'adresse, la photo, le pseudo, la note et les avis du vendeur.
- **Photo d'une recherche par photo jamais conservée** : ni en base (`track_photo_searches` n'a pas de colonne photo : description lue et estimation seulement), ni sur le disque, ni dans un journal ; un message d'erreur ne la reprend jamais. Photo JPEG, PNG ou WebP (contrats) ; côté API, livrée en parallèle : une seule photo, 1,5 Mo au plus, 10 recherches par minute et par membre. La lecture compte dans le quota IA.
- **Lecture en direct fermée par défaut** (`TRACK_LIVE_ENABLED=false`) : simulateur, données marquées « démonstration ». Ouverte, elle ne lit que des pages **publiques** du catalogue, **sans session ni cookie**, avec le lecteur et le navigateur de Selio Cloud (bac à sable, environnement minimal, aucune option de furtivité, User-Agent d'origine, aucun proxy) ; au premier signal de Vinted, pause de Track écrite d'abord, ralentissement, coupe-circuit de la machine pour un blocage ou un « trop de requêtes » ; rien n'est retenté ni contourné. Usage des données issues de Vinted **à valider juridiquement**.
- **Analyse d'un vendeur concurrent** : non construite (409, puis 501 si `TRACK_SELLER_ANALYSIS_ENABLED=true`) ; aucun pseudo n'est lu ni gardé.
- **RLS** : `track_filters`, `track_scans`, `track_photo_searches` ont la politique `org_isolation` forcée pour `selio_app` (`0013_track_pricing.sql`, testé). `track_snapshots`, `price_references` et `price_models` sont partagées et ne contiennent aucune donnée d'organisation ni de personne.
- **Journaux** : empreintes abrégées, codes et compteurs ; jamais de titre, de pseudo, de photo ni d'adresse d'annonce. Le rapport d'entraînement du modèle de prix ne contient que des volumes et des mesures.
- **Mon IA perso n'écrit pas les prix** (D07) : son explication est écartée si elle cite un montant ou un chiffre absent des faits fournis ; elle n'est jamais bloquante.
- **Panneau des comparables de l'extension** : seuls le titre, la marque, la catégorie (vide avec l'adaptateur v1), la taille, l'état et le prix de l'article quittent la page, jamais le pseudo du vendeur, les photos, la description, l'adresse ou la référence de l'annonce. Le schéma est strict au départ du content script, **revalidé par le service worker** (seul détenteur du jeton) avant l'appel, et la réponse est revalidée avant d'être affichée (texte seulement, jamais d'HTML). La route `POST /api/ext/comparables` exige la portée `capture:items`, le droit `items.read` et une offre avec Track (402 sinon), avec 30 appels par minute et par membre au plus ; elle **n'enregistre rien**. Seul le vecteur du titre (modèle 2) peut être gardé dans `embeddings_cache` de l'organisation (RLS), sous l'empreinte du texte, sans le texte.

## Journal d'audit
Actions sensibles (connexion, membres, règles, jetons, connexions, exports, suppression, changements de plan par l'opérateur, Selio Cloud, Selio Radar et ses achats, filtres Track coupés par l'offre) dans `audit_logs`, sans contenu de message ni secret. Durées de conservation configurables par organisation ; nettoyage quotidien par le worker.

## Sauvegardes et restauration
Procédure complète : SAUVEGARDE.md (scripts dans `scripts/sauvegarde/`).
- Chaque nuit : `pg_dump --format=custom` et photos MinIO, **chiffrés avec age** : la machine ne détient que la clé publique, la clé privée est sur le portable de secours et sur papier. À défaut, gpg symétrique. Rien n'est écrit en clair sur le disque. Sommes SHA-256, copie hors machine avec rclone, rotation 30 jours.
- La sauvegarde se fait avec le rôle propriétaire (superutilisateur ou BYPASSRLS), jamais avec `selio_app` : la RLS forcée rendrait les tables vides. Le script le vérifie.
- Test de restauration mensuel dans une base temporaire (`selio_restore_test`, nom imposé pour ne jamais viser la production), comparé à un manifeste chiffré écrit dans le même instantané que le dump.
- Les sessions Cloud sont dans la sauvegarde, chiffrées. La clé `SECRETS_ENCRYPTION_KEY` et les `.env` ne le sont pas : copie chiffrée à part, à la main. Sans la clé, les secrets de connexion et les sessions Cloud sont irrécupérables (par conception : les clients se reconnectent).

## Limites connues
- Pas de 2FA. Réinitialisation du mot de passe et invitations par email : jetons de 32 octets à usage unique dont seule l'empreinte SHA-256 est stockée (1 h / 7 jours), réponse de « mot de passe oublié » identique et à temps constant qu'un compte existe ou non, pages web qui retirent le jeton de l'adresse avant le rendu. Tant que `EMAIL_PROVIDER=noop` (défaut, signalé au démarrage en production), aucun email ne part : le service d'email reste à choisir.
- Stockage des photos : URLs signées (SigV4) vers un stockage S3 compatible sur notre machine, type et taille imposés par la signature, clés `org/<orgId>/…` vérifiées ; côté API prêt (`/api/uploads`), l'envoi depuis le navigateur reste à brancher et, sans `STORAGE_ENDPOINT`, les photos restent des URL/data URL dans la base.
- Selio Cloud : jamais exécuté contre Vinted ; les sélecteurs propres au Cloud et les motifs de détection des blocages ne sont pas vérifiés sur le vrai site ; activation client seulement après l'avis de l'avocat (CLOUD.md §6).
- Selio Radar : jamais exécuté contre Vinted ; sélecteurs du catalogue et du paiement écrits sur fixtures synthétiques ; la reprise d'un paiement 3-D Secure ne vit que dans la mémoire du worker (après un redémarrage : « effets inconnus », le client vérifie dans Vinted, rien n'est racheté) ; le texte de l'accord Cloud ne mentionne pas encore Radar (RADAR.md §8 et §9).
- Selio Track : jamais exécuté contre Vinted ; lecture en direct testée seulement avec un lecteur simulé, sélecteurs du catalogue écrits sur fixtures synthétiques ; une annonce « disparue » peut avoir été retirée (prix final estimé, présenté comme tel) ; avis de l'avocat attendu sur la collecte et l'usage des données (TRACK.md §6 et §7). Aucun chiffre du modèle de prix n'est une mesure réelle (PRIX.md §13).
- Sauvegarde : perte possible jusqu'à 24 h (pas d'archivage continu des WAL) ; rclone réel et mode Docker non essayés dans le conteneur de développement (SAUVEGARDE.md).
- Paiement : la purge des données après `data_retention_until` (30 jours après le retour à l'accès de base) n'est pas encore une tâche du worker (suppression ou anonymisation à décider) ; le prélèvement SEPA pour l'annuel n'est pas implémenté ; changer de carte alors qu'une carte est déjà enregistrée passe par le support (l'API ne rouvre pas de formulaire dans ce cas).
