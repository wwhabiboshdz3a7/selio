# Journal des décisions

Format : contexte → décision → conséquences. Les décisions sont datées du 8 octobre 2026 sauf mention contraire.

## D01 — Repartir du dépôt v1 comme source d'inspiration, pas comme base
Le dépôt contenait un MVP « marketplace » (charte bleue, Playfair, scène 3D) contraire aux guidelines v2 et au produit visé (outil de gestion). **Décision** : suppression du code v1, conservation des idées éprouvées (sessions cookie HttpOnly, hachage scrypt, format fr-FR, Netlify). **Conséquence** : aucune dette visuelle héritée ; l'historique Git conserve la v1.

## D02 — Tailwind v4 avec un thème CSS miroir du preset v3
Le preset livré cible Tailwind v3 (`module.exports`, `presets`). **Décision** : Tailwind v4 (CSS-first) avec `packages/ui/src/styles/theme.css` (`@theme inline`) reproduisant exactement le preset ; le preset est conservé, converti en ESM et corrigé, pour un éventuel projet v3. **Corrections documentées** : `module.exports` → `export default` (monorepo en `type: module`) ; ajout de `inherit` et des gris 300/400/900 (graphiques, toggles) ; `--spacing: 4px` pour garder la grille de 4 px malgré la taille racine de 14 px imposée par tokens.css ; palette Tailwind par défaut retirée (`--color-*: initial`) pour garantir l'absence de bleu.

## D03 — tokens.css : police auto-hébergée
Le fichier livré chargeait Inter depuis Google Fonts (requête tierce, PWA hors-ligne impossible, CSP). **Décision** : retrait de l'`@import` externe, Inter 400/500/600 via `@fontsource/inter`, ajout de `color-scheme` pour les contrôles natifs. Le reste du fichier est inchangé.

## D04 — Logos
Les PNG officiels (4×) sont fournis dans `brand/`. **Décision** : utilisation des PNG (noir sur fond clair, blanc sur fond sombre) dans la vitrine et l'application ; un wordmark SVG monochrome sert de repli (extension, favicon, contextes où un PNG serait flou). **Asset manquant** : la source vectorielle `logo-principal.svg` mentionnée dans les guidelines n'est pas fournie ; les favicons sont dérivés des PNG.

## D05 — PostgreSQL « compatible Supabase » plutôt que le SDK Supabase
**Décision** : PostgreSQL via `pg`, migrations SQL versionnées, authentification maison (scrypt + sessions), RLS forcée pour un rôle applicatif non superuser. La base peut être hébergée chez Supabase (Postgres managé) sans dépendance au SDK ni à Supabase Auth. **Conséquence** : environnement local 100 % Docker, tests d'isolation exécutables partout.

## D06 — Deux implémentations d'un même `DataClient`
**Décision** : l'application web parle à une interface unique ; `DemoClient` tourne dans le navigateur (localStorage, règles `domain`, simulateurs déterministes) et `ApiClient` appelle l'API. **Conséquence** : la démo prouve les règles métier avec le même code que le serveur ; aucun repli silencieux (le mode connecté sans API affiche un message honnête).

## D07 — L'IA rédige, la politique décide
**Décision** : `evaluateOffer` (déterministe) tranche avant tout appel IA ; la sortie IA est validée par schéma puis par politique ; en production (`ALLOW_AI_FALLBACK=false`, `AI_PROVIDER≠mock` imposés), une panne IA produit une erreur explicite. Les automatisations utilisent des gabarits déterministes et continuent sans IA.

## D08 — Connecteur Vinted = extension, expérimental, non vérifié
Pas d'API publique vendeur, pas d'OAuth officiel. **Décision** : le serveur ne possède jamais de session Vinted ; l'extension lit la page ouverte via des adaptateurs DOM versionnés testés sur fixtures synthétiques ; `send_message` est **indisponible** côté serveur (le texte est inséré, l'utilisateur envoie). Statut annoncé partout : expérimental, à valider en navigateur réel.

## D09 — File de tâches : BullMQ pour le déclenchement, table `jobs` pour l'état
**Décision** : la table `jobs` est la source de vérité observable (clé d'idempotence, tentatives, résultat) ; BullMQ (Redis) ne porte que les planifications répétables. Sans Redis, l'API fonctionne en mode inline (exécution immédiate) — documenté.

## D10 — Paiement : Stripe REST minimal, mode test imposé
**Remplacée par D24 (29 octobre 2026) : Stripe retiré, Revolut par défaut derrière une interface `PaymentProvider`.** Décision d'origine : pas de SDK ; vérification de signature HMAC et idempotence par identifiant d'événement ; clé live refusée sans `STRIPE_LIVE_ALLOWED=true`. Aucun abonnement n'est créé sans configuration explicite. Les principes (pas de SDK, signature vérifiée, idempotence, mode live refusé par défaut) sont repris tels quels avec Revolut.

## D11 — Achat assisté simulé, achat réel désactivé
**Décision** : workflow complet (budget, prix max, contrôles, doublons) avec exécution simulée ; `realPurchaseEnabled=false` sans possibilité de l'activer depuis l'interface tant qu'aucun connecteur autorisé n'existe. Aucun endpoint d'achat n'est improvisé.

## D12 — Secrets
Infrastructure : variables d'environnement validées au démarrage. Par organisation : chiffrement AES-256-GCM (`SECRETS_ENCRYPTION_KEY` hors base). Jetons d'extension hachés, affichés une fois, portées limitées, expiration 90 jours, révocation.

## D13 — Instantanés dans le client de démonstration (correctif)
Le cache de requêtes partageait les objets mutés en place par `DemoClient`, rendant certains changements invisibles aux effets React. **Décision** : toute valeur renvoyée par `DemoClient` est clonée (`structuredClone`) via un proxy.

## D14 — Tarifs
Structure à trois plans avec quotas dans `contracts` ; montants de la vitrine **indicatifs** (`VITE_SHOW_INDICATIVE_PRICING`). Aucun avis client, chiffre d'utilisateurs ou partenariat n'est affiché.
**Mise à jour (18 octobre 2026)** : les offres ne sont plus présentées comme des listes de quotas « X par mois ». **Découverte** est un essai gratuit **temporel** (1 semaine par défaut, ou 1 mois, `TRIAL_DAYS_OPTIONS`) donnant les fonctions et limites du plan Pro, sans carte ; la durée est choisie sur Tarifs ou à l'inscription (`registerInput.trialDays`) et l'inscription crée l'abonnement « trialing » correspondant. Tant que les abonnements payants ne sont pas ouverts, la fin d'essai n'est pas appliquée (dit dans l'interface et la FAQ). Essentiel et Pro sont décrits par profil et par ce qu'ils permettent (comptes Vinted, équipe, modules, assistance) dans `packages/demo-data/src/plans.ts` ; les limites techniques restent dans `PLAN_QUOTAS` et s'affichent dans l'application en pourcentage. Le plan `free` (sans abonnement) s'appelle « Accès de base » pour ne pas être confondu avec l'essai.

## D16 — Aide : une FAQ partagée, l'IA bornée aux passages, la vitrine sans IA
**Contexte** : une aide « avec de l'IA qui pourrait répondre », sans promettre ce qui n'existe pas. **Décision** : le contenu (questions, réponses, catégories) et la recherche (normalisation, racines, synonymes, score) vivent dans `packages/domain/src/help.ts`, sans dépendance, importé par la vitrine (/faq), l'application (/app/help) et le serveur ; les chiffres cités viennent des constantes du code. La route `POST /api/help/ask` **exige une session** (tous rôles, lecture seule comprise) et est limitée à 10 questions par minute : la vitrine publique ne l'appelle pas et répond par la même recherche, localement, sans IA anonyme (coût, abus, file Ollama partagée avec les organisations). Le serveur ne transmet à l'IA que les passages retenus (`help_answer`) ; la sortie est validée (aucun lien, adresse ni HTML, sources parmi les passages, aucun chiffre absent des passages, vocabulaire tiré d'eux, motifs d'injection écartés). IA désactivée, indisponible ou sortie écartée : la réponse de la FAQ s'affiche, **signalée comme telle** — ce n'est jamais un texte simulé présenté comme venant du modèle, d'où un repli permis même en production. Sans passage pertinent, aucun appel à l'IA : « pas de réponse dans l'aide ». Les questions d'aide sont journalisées (état de l'IA) mais **non décomptées** du quota IA mensuel. En démonstration, `DemoClient.askHelp` répond depuis la FAQ, signalé.

## D15 — Bundles esbuild pour l'API et le worker
La sortie `tsc` d'un monorepo ESM n'est pas exécutable telle quelle (imports sans extension, paquets `@selio/*` pointant vers des sources TypeScript). **Décision** : `pnpm build:api` et `pnpm build:worker` produisent des bundles ESM Node 22 avec esbuild (`apps/*/scripts/build.mjs`) : dépendances npm externes, paquets internes inclus, source maps. L'API expose aussi `dist/migrate.js` et `dist/seed-demo.js` pour les conteneurs. Le typage reste vérifié par `pnpm typecheck` ; le développement utilise `tsx` sans bundle.

## D16 — Espaces Selio : un accueil central, quatre espaces, une seule application
**Décision** : Selio (outil de gestion, `/app`), Selio Studio (`/studio`), Selio Agence (`/agence`, aperçu) et Selio Global (`/global`, en préparation) partagent la même session, la même mise en page et le même `DataClient` ; seul le menu change (sélecteur d'espace en tête du menu latéral, teinte d'identité par `data-space`). L'accueil central `/app/espaces` devient la page d'arrivée après connexion et depuis `/demo` ; Paramètres et Administration sont communs et gardent l'espace courant. Studio lit les données existantes (articles, ventes, dressing) et calcule « Ce qui performe » dans `domain/listing-insights` (aucun chiffre inventé). Agence n'a qu'une donnée propre, la marque blanche, enregistrée dans la démonstration seulement (`DemoState.whiteLabel`, état v8) ; en mode connecté elle se prévisualise sans s'enregistrer (erreur `preview_only`) et aucune route serveur n'est ajoutée. Les boutiques clientes et la facturation de l'agence sont des exemples fictifs marqués comme tels. Global ne relie aucun marché ni aucune place de marché : seuls le convertisseur de tailles et les repères par pays sont utilisables.

## D17 — Trois modèles d'IA, un routage par tâche (28 octobre 2026)
**Contexte** : le compte rendu de réunion fixe trois rôles sur la machine de Marseille : mon IA perso (texte, nom donné à part par Ibrahim), le modèle 1 pour les photos (`qwen3-vl:8b`) et le modèle 2 pour les prix (`qwen3-embedding:0.6b`), tous via Ollama ; les trois doivent rester chargés (16 Go de carte). **Décision** : un seul `OllamaProvider` avec trois variables (`OLLAMA_MODEL`, `OLLAMA_VISION_MODEL`, `OLLAMA_EMBED_MODEL`, les deux dernières avec une valeur par défaut, désactivables en les laissant explicitement vides) ; c'est le code qui route, jamais l'utilisateur : requête avec images → modèle 1, `AIService.embed` → modèle 2 (`POST /api/embed`), tout le reste → mon IA perso. La santé (`/api/ai/health`) vérifie les trois modèles (`healthy` / `degraded` / `unavailable`) ; `pnpm ai:diagnose` et `pnpm ai:bench` (modes `reply`, `photo`, `embed`) mesurent sur place. Une file et un disjoncteur communs (un seul serveur), mais le disjoncteur ignore les erreurs de configuration (`model_missing`, `config`), les sorties invalides, les annulations et les quotas : seules les pannes du serveur l'ouvrent. **Conséquences** : un modèle secondaire non installé dégrade la fonction concernée (Studio : 503 `model_missing` ; embeddings : erreur explicite) sans couper les réponses aux acheteurs ; aucun vecteur ni texte simulé en production ; le modèle 2 n'a pas encore de consommateur (estimation des prix, 5.10) et ne passe pas par les quotas, qui sont appliqués côté `core` par comptage des `ai_requests` ; les repères (≈ 15 réponses / min, ≈ 3,6 s / photo) restent à confirmer par la mesure.

## D18 — Offres 1 / 3 / 10, essai de 14 jours, aucun compte à la carte (28 octobre 2026)
**Contexte** : la réunion a tranché les offres (Starter 6,99 €, 1 compte, 300 réponses ; Pro 24,99 €, 3 comptes, 1 500 réponses, 20 annonces et 10 photos portées Studio, Track essentiel, relance proposée ; Agence 49,99 €, 10 comptes, 5 000 réponses, 60 / 30 Studio, Track complet, relance automatique, Cloud inclus, rôles d'équipe), au-delà de 10 comptes sur devis, aucun compte supplémentaire à la carte, et remplace l'essai Découverte (7 ou 30 jours) par un essai unique de 14 jours avec carte enregistrée, rien débité avant la fin. **Décision** : « Essentiel » devient `starter`, le plan `agence` s'ajoute ; `PLAN_QUOTAS` porte les limites par filiale (`studioListingsPerMonth`, `wornPhotosPerMonth`, `trackFiltersFollowed`, `trackScansPerMonth`, `trackPhotoSearchesPerMonth`, `trackHistoryMonths`, `cloudIncluded`, `followUp24h`) ; `TRIAL_DAYS = 14` est la seule durée (7 et 30 envoyés par un ancien client web sont ramenés à 14), l'inscription crée l'abonnement `trialing` au plan Pro avec `cardOnFile=false` tant que le paiement n'est pas branché. Les montants (abonnements, annuel = 10 mois, fondateurs −30 % / 6 mois et 1 mois offert sur Starter, Studio seul au curseur avec plancher 0,02 € la photo et 4,99 € minimum, Radar 14,99 €, Radar Auto 29,99 €, Cloud en option 9,99 €, Selio Comptes 9,99 € / 14,99 €) vivent dans `PRICING` (`packages/demo-data/src/plans.ts`), marqués indicatifs, jamais en dur dans un composant ; le devis Studio seul est interpolé entre les packs pour que le prix croisse toujours avec le nombre de photos. Un abonnement créé avant ces offres (JSON `quotas` sans champs par filiale : 3 000 réponses, 5 comptes, 10 membres pour l'ancien Pro) ne vaut pas « sur mesure » : il est remplacé par les quotas de son plan à la lecture (`resolveQuotas`) et en base par la migration 0008 ; un JSON complet (devis) est conservé. **Conséquences** : libellés, aide, tests et client de démonstration alignés ; aucun prix n'est définitif ; la fin d'essai et l'enregistrement de la carte attendent le paiement Revolut ; un ancien Pro retrouve Studio (20 annonces) et les nouvelles limites (1 500 / 3 / 3) sans intervention manuelle.

## D19 — Compteurs par filiale, page « Mon utilisation », vue administrateur (28 octobre 2026)
**Contexte** : chaque filiale a ses quotas mensuels (annonces et photos portées Studio, scans et recherches par photo Track, actions Cloud par jour) et la réunion demande une page par client avec une barre par filiale et une alerte à 80 %, plus une vue de l'usage par client pour l'opérateur. **Décision** : les événements `usage_events` reçoivent les sortes `studio.listing`, `studio.worn_photo`, `track.scan`, `track.photo_search`, `cloud.action` ; `getUsage` (core) et le client de démonstration construisent la même forme (`counters` + `studio` / `track` / `cloud`, `buildUsageCounter` : utilisé / quota / pourcentage plafonné / alerte à 80 % / dépassé) avec une remise à zéro le 1er du mois UTC (date anniversaire à décider, docs §7) ; chaque action vérifie son compteur avant d'agir (Studio : « non inclus » si le quota est 0, « quota du mois atteint » sinon). Le compteur « Réponses de mon IA perso » suit la règle du refus : lignes `ai_requests` du mois (échecs compris, questions d'aide exclues) face au plus petit entre le quota du plan et `settings.ai.monthlyRequestQuota` (500 par défaut), partout (page, abonnement, vue administrateur, démo). La vue administrateur lit une fonction SQL `SECURITY DEFINER` (`app_admin_org_usage`, 0006 puis 0008) qui résume toutes les organisations sans ouvrir les tables isolées par RLS, triée du client le plus proche de sa limite. **Conséquences** : jamais « 33 % » affiché pendant qu'une requête est refusée ; les filtres Track suivis n'ont pas encore de stockage (0 utilisé, quota affiché) ; la démo garde quatre comptes Vinted pour un quota Pro de 3 (« Limite atteinte »), à trancher.

## D20 — Gabarits de contre-offre : « dernier prix » seulement au plancher (28 octobre 2026)
**Contexte** : les messages disaient « c'est mon meilleur prix » ou « c'est mon dernier prix » alors que le plancher pouvait être plus bas, et « l'article est en très bon état » sans le savoir. **Décision** : une seule fonction `counterOfferWording(counterCents, floorCents)` (`@selio/ai`) partagée par les automatisations, le gabarit sans IA, la messagerie, la démo et le seed : au plancher « Je peux aller jusqu'à X €, c'est mon dernier prix pour cet article. Si cela vous convient, faites l'offre à ce montant. », au-dessus la formule neutre « Je peux vous le faire à X €. Si cela vous convient, faites l'offre à ce montant. » ; plus aucune mention de l'état. Le vrai modèle reçoit la même règle (`SYSTEM_REPLY` : jamais « meilleur prix », « dernier prix » seulement si la consigne le dit) et `buildReplyRequest` n'autorise la formule — et n'émet l'indice `[[atFloor: 1]]` lu par le simulateur — que si la contre-offre de la politique est au plancher ; `validateReplySuggestion` rejette (`false_last_price`) tout « meilleur prix » et tout « dernier prix » hors de ce cas. **Conséquences** : automation, mock et vrai modèle disent la même chose sur le même cas ; un brouillon qui affirmerait un faux dernier prix n'atteint jamais l'acheteur ; les réglages `negotiation.messages.counter` / `final` de l'organisation portent les nouveaux textes par défaut.

## D21 — Stockage des photos : S3 compatible sur notre machine, URLs signées (28 octobre 2026)
**Contexte** : les photos doivent rester en France, sans service payant, sans transiter par l'API ; la réunion retient un stockage objet compatible S3 hébergé sur la machine de Marseille. **Décision** : `packages/storage` signe lui-même (SigV4 en paramètres de requête, `node:crypto`, aucun SDK) des URLs `PUT` et `GET` de courte durée (`STORAGE_PRESIGN_TTL_SECONDS`, 900 s) vers MinIO (`docker compose up -d minio` en local, Caddy devant en production) ; l'API (`/api/uploads/policy`, `/presign`, `/read`) valide sorte (`item-photo`, `studio-photo`, `avatar`), type (JPEG / PNG / WebP) et taille (5 Mo) avant de signer, impose `Content-Type` et `Content-Length` dans la signature, génère la clé `org/<orgId>/<kind>/<uuid>.<ext>` sans nom de fichier utilisateur, ne relit que les clés de l'organisation de la session, journalise chaque demande et n'émet jamais d'URL publique. Sans `STORAGE_ENDPOINT`, le stockage est désactivé (503 `storage_unconfigured`, signalé au démarrage) ; une configuration à moitié remplie arrête le démarrage. **Conséquences** : un autre fournisseur compatible S3 se branche en changeant quatre variables ; l'envoi depuis le navigateur (presign → PUT → clé enregistrée sur l'article) et le déploiement de MinIO restent à faire ; les droits suivent `items.write` (le futur rôle « contributeur photos » se branchera là).

## D22 — Emails transactionnels : interface de fournisseur, « noop » par défaut, service à valider (28 octobre 2026)
**Contexte** : invitations, mot de passe oublié, échec de paiement et alertes ont besoin d'emails, mais le service d'envoi doit être validé par Ibrahim avant tout branchement, et aucun service payant n'est engagé. **Décision** : `packages/email` expose une interface `EmailProvider` et des gabarits (texte + HTML échappé, liens http(s) seulement, aucune image ni script) ; deux fournisseurs : `noop` (défaut : journalise l'adresse masquée, jamais le contenu ; garde les derniers messages pour les tests) et `smtp` (nodemailer, `SMTP_URL` seule porteuse des identifiants, STARTTLS **imposé** pour `smtp://` — jamais de repli en clair si le serveur n'annonce pas la capacité —, TLS direct pour `smtps://`, délais 10 / 10 / 15 s). En production, `noop` est accepté mais signalé au démarrage. L'envoi se fait toujours **après** la transaction PostgreSQL et, pour « mot de passe oublié », **hors du chemin de la réponse** (204 à temps constant, plancher 300 ms) ; une invitation dont l'email ne part pas est défaite (jeton invalidé, appartenance retirée, compte créé pour l'occasion supprimé) et répond 503 `email_unavailable`. **Conséquences** : aucune connexion du pool retenue par un serveur SMTP lent, aucune énumération des comptes au chronomètre ; le choix du service (SMTP maison, relais) reste à faire avec Ibrahim, puis SPF / DKIM sur le domaine de `EMAIL_FROM` ; l'email d'échec de paiement attend le flux Revolut.

## D23 — Jetons envoyés par email : hachés, à usage unique, retirés de l'adresse (28 octobre 2026)
**Contexte** : réinitialisation de mot de passe et invitations passent par un lien reçu par email ; ce lien ne doit ni fuiter ni resservir. **Décision** : jeton de 32 octets aléatoires en base64url, jamais stocké ni journalisé — seule son empreinte SHA-256 l'est (`password_resets`, `invites`, migration 0007, tables globales hors RLS comme `users` et `sessions`) ; durée de vie 1 heure (mot de passe) et 7 jours (invitation) ; une seule demande valable à la fois par utilisateur ; consommation en une transaction (mot de passe changé ou défini, jeton marqué utilisé, autres jetons invalidés, **toutes les sessions du compte fermées**) ; une réponse unique `token_invalid` (400) sans distinguer inconnu, expiré ou déjà utilisé ; limites de débit par adresse IP sur les routes. Côté web, les pages `/mot-de-passe` et `/invitation` lisent le jeton puis le retirent de l'adresse (`history.replaceState`) avant le premier rendu, pour qu'il ne reste ni dans l'historique, ni dans un en-tête Referer, ni dans les journaux de l'hébergeur statique ; la démonstration n'émet aucun lien et le dit. **Conséquences** : un jeton volé après usage ne sert à rien ; les liens sont inutilisables sans API (`VITE_API_BASE_URL`) ; la page de connexion propose « Mot de passe oublié ? » ; la FAQ et docs/SECURITY.md décrivent le flux tel qu'il existe.

## D24 — Paiement : Stripe retiré, Revolut Merchant API par défaut derrière une interface `PaymentProvider` (29 octobre 2026)
**Contexte** : la réunion a retenu Revolut Business (compte marchand) pour encaisser les abonnements : formulaire intégré (carte, Apple Pay, Google Pay, Revolut Pay), carte enregistrée « pour le marchand », débit mensuel par l'API depuis le worker, 1 % + 0,20 € par carte européenne, argent réglé sous 24 h ; l'adaptateur Stripe de test ne devait pas rester. L'environnement de test Revolut n'est pas joignable depuis la machine de développement. **Décision** : l'adaptateur Stripe est supprimé (code, tests, migration, docs ; D10 est caduque) et remplacé par une interface neutre `PaymentProvider` (`packages/connectors/src/payments/types.ts`) dont `RevolutClient` est la seule implémentation (REST sans SDK, `Authorization: Bearer sk_…`, `Revolut-Api-Version` configurable, bac à sable par défaut, `REVOLUT_MODE=live` refusé sans `REVOLUT_LIVE_ALLOWED=true`) ; Mollie pourra se brancher en secours derrière la même interface. Le navigateur ne reçoit que le jeton public d'une commande ; aucun numéro de carte ne transite par Selio ; tout est testé sur un HTTP simulé (client Revolut réel, en-têtes et signatures compris).
**Essai** : la carte est enregistrée par une commande de **vérification de 1 €** en capture manuelle (`CARD_VERIFICATION_AMOUNT_CENTS`, jamais le prix de l'offre), annulée dès le webhook `ORDER_AUTHORISED` ; la carte retenue est celle de la tentative aboutie, lue sur la commande (une première carte refusée dans le même formulaire ne bloque pas la seconde) ; une panne passagère de Revolut pendant le webhook répond 5xx (Revolut relivre) au lieu de conclure « aucune carte » ; une autorisation non annulée est réannulée par le worker à chaque passage ; une capture inattendue n'active rien, n'émet aucune facture et est journalisée pour remboursement manuel. Le même parcours sert à « Changer de carte » (`POST /api/billing/card`, sorte `card_update`) ; en retard de paiement, le débit est retenté dans l'heure.
**Relances** : J+1, J+3, J+7 après l'échéance, à l'heure de l'échéance, avec un email à chaque échec ; la tâche `billing.renew` tourne **toutes les heures** (un passage quotidien décalait les tentatives d'un jour par rapport aux dates annoncées). Après la troisième relance : accès de base, données conservées 30 jours, **carte oubliée** (le prochain paiement enregistre celle que le client saisit). Une commande jamais présentée à la banque (panne entre la création et le débit) est remplacée sans compter d'échec ; une commande restée en traitement plus de 20 h est annulée chez Revolut avant d'être comptée échouée (jamais de double débit) ; une période déjà payée n'est jamais raccourcie (409 depuis le formulaire, prolongation sinon).
**Factures** : `SEL-AAAA-000001`, continues par année, émises par l'API (webhook `ORDER_COMPLETED`) ou par le worker (renouvellement) ; la clôture d'une commande est un `UPDATE … WHERE state <> 'completed' RETURNING` dans la transaction (une seule facture même si worker et webhook se croisent), `invoices.order_id` est unique, le numéro vient d'un compteur transactionnel `invoice_counters` (migration 0010, reprise des séquences 0009 sans rupture ; une transaction annulée rend son numéro) ; les webhooks sont réservés atomiquement (`payment_events.claimed_at`) et une réservation dont le traitement échoue est relâchée. TVA 20 % ou franchise en base (`FRANCHISE_TVA`) ; rendu imprimable côté web avec les mentions `VITE_INVOICE_ISSUER_*`. **Conséquences** : webhook à créer une fois par environnement chez Revolut (`REVOLUT_WEBHOOK_SECRET`), parcours à valider en bac à sable avec les cartes de test, prélèvement SEPA annuel (0,6 % plafonné à 5 €) et purge des données après `dataRetentionUntil` encore à faire.

## D25 — Selio Cloud : navigateur ouvert seulement pour agir, contexte sans enregistrement, session chiffrée par compte (29 octobre 2026)
**Contexte** : le prompt (§5.7) demande « un profil Chromium isolé par compte », une session chiffrée supprimable, et un navigateur ouvert seulement pour agir ; une revue a montré qu'un profil persistant écrivait la session en clair sur le disque (base SQLite des cookies) et que Chromium tournait sans bac à sable avec tout l'environnement du worker. **Décision** : l'isolation par compte est portée par la **session** (cookies et stockage local des domaines Vinted d'une liste fermée, sans cookie de passage anti-robot), chiffrée par `SecretBox` (clé `SECRETS_ENCRYPTION_KEY`, données associées = identifiant du compte Cloud) dans `cloud_accounts.session_ciphertext`, et non par un profil disque gardé entre deux actions. Pour chaque action : `chromium.launch` avec **bac à sable actif** (vérifié au démarrage, Cloud désactivé sinon, `CLOUD_CHROMIUM_SANDBOX=false` refusé en production), **environnement en liste blanche** (aucune variable du worker), `browser.newContext` **sans enregistrement** (session en mémoire), dossier de travail temporaire (HOME / TMPDIR, 0700, tmpfs conseillé) supprimé à la fin ; tout est refermé ensuite, aucun processus permanent par compte. La session n'est réécrite après une action que si c'est encore celle du début (relue sous verrou). **Conséquences** : rien de la session ne touche le disque ; une faille d'un moteur de rendu n'expose ni la clé ni la base ; le worker doit tourner hors root avec les espaces de noms utilisateur permis (profil seccomp adapté en Docker) ; `CLOUD_PROFILE_DIR` est réservé à un seul worker (balayé entièrement au démarrage, puis à chaque passage).

## D26 — Selio Cloud : connexion par fenêtre sécurisée (capture CDP relayée) plutôt que par export de session de l'extension (29 octobre 2026)
**Contexte** : deux façons d'obtenir la session d'un compte : exporter les cookies du navigateur du client par l'extension, ou le laisser se connecter lui-même dans un navigateur du Cloud. **Décision** : fenêtre de connexion sécurisée. Le worker ouvre Chromium sur la page de connexion de Vinted, filme la page (CDP `Page.startScreencast`, JPEG qualité 60, 2 à 4 images/s) et rejoue les clics et frappes du client (CDP `Input.*`), relayés par l'API (WebSocket) et Redis pub/sub, validés deux fois, jamais journalisés. Ticket aléatoire montré une fois, haché en base, valable 5 min, **à usage unique** ; fenêtre annulée dès que la WebSocket se ferme ; cadre principal limité aux pages https de Vinted et des fournisseurs de connexion, **redirections revérifiées**, réseau local bloqué ; au plus 2 fenêtres par organisation et `CLOUD_MAX_BROWSERS - 1` sur la machine. L'export par l'extension est écarté : il ferait sortir de l'ordinateur du client une session créée ailleurs (autre adresse, autre empreinte), il demanderait à l'extension un droit de lecture des cookies (collecte plus large que nécessaire) et il ne laisse aucune trace d'un consentement donné au moment de la connexion. **Conséquences** : aucun mot de passe Vinted ne transite ailleurs que dans les frappes relayées ; connexion Google / Facebook / Apple non prise en charge (fenêtres surgissantes fermées) ; un CAPTCHA pendant la connexion ferme la fenêtre (D28).

## D27 — Selio Cloud : adresse partagée, actions légères seules, lourdes derrière `CLOUD_HEAVY_ACTIONS`, coupe-circuit de la machine (29 octobre 2026)
**Contexte** : au lancement, tous les comptes Cloud sortent par l'adresse IP de la machine de Marseille ; un compte sanctionné peut faire bloquer l'adresse pour tous. **Décision** : seules les actions **légères** (répondre, relancer après 24 h) sont permises ; les **lourdes** (republier, modifier en masse) sont refusées à trois endroits (réglage du compte, planificateur, exécuteur) tant que `CLOUD_HEAVY_ACTIONS=false`, **à décider par Ibrahim**. 10 comptes Cloud au plus par organisation (`CLOUD_MAX_ACCOUNTS_PER_ORG`), plafond revérifié à chaque action. Ajout de la revue : après un « trop de requêtes » ou un blocage sur un compte, **coupe-circuit** de toute la machine pendant 60 min (`cloud_runtime`, `CLOUD_CIRCUIT_BREAKER_MINUTES`), alerte de l'opérateur dans le journal du worker ; à valider avec Ibrahim (le prompt ne prévoyait qu'une pause par compte). Radar Auto n'est pas concerné. **Conséquences** : un signal de Vinted n'est jamais suivi d'autres requêtes depuis la même adresse dans l'heure ; la levée anticipée est manuelle (`update cloud_runtime set suspended_until = null`).

## D28 — Selio Cloud : pause au premier avertissement, sans nouvelle tentative (29 octobre 2026)
**Contexte** : aucun contournement de CAPTCHA ni de protection anti-robot n'est acceptable (étude juridique). **Décision** : `detectBlock` (motifs lisibles, scripts et corps des messages ignorés) sert uniquement à s'arrêter. Au premier CAPTCHA, avertissement, blocage ou « trop de requêtes » — pendant une action, **après une exception** (la page est relue avant de conclure « erreur ») ou **pendant la connexion** — le compte passe en pause avec la raison, la pause est écrite **seule et d'abord** (elle survit à un échec de l'enregistrement du reste), les propriétaires reçoivent un email, rien n'est retenté ; la reprise exige un acquittement explicite du client, et une nouvelle fenêtre de connexion aussi. Pendant la connexion, la fenêtre est fermée **sans enregistrer la session** ; les cookies de passage anti-robot ne sont jamais gardés. Une action interrompue par l'arrêt brutal du worker met le compte en pause « interrupted ». Aucun plugin « stealth », User-Agent ni empreinte modifiés. **Conséquences** : si Vinted affiche une vérification à chaque connexion, le Cloud est inutilisable pour ce compte — c'est voulu ; l'assouplissement éventuel reste une décision d'Ibrahim. Motifs construits sans page réelle, à compléter dès qu'un vrai signal est observé.

## D30 — Selio Cloud : sauvegarde chiffrée nocturne, test de restauration mensuel, aucune reprise automatique après restauration (29 octobre 2026)
**Contexte** : les sessions chiffrées vivent dans PostgreSQL ; une restauration ranimerait des comptes arrêtés et des sessions supprimées depuis la sauvegarde. **Décision** : sauvegarde nocturne (03:30) de la base et des photos, chiffrée avec age (clé privée hors de la machine), copie hors machine par rclone, rotation 30 jours ; test de restauration le 1er du mois, de préférence sur le portable de secours, comparé à un manifeste ; `SECRETS_ENCRYPTION_KEY` et les `.env` hors sauvegarde automatique (copie chiffrée à part). **Toute restauration** (bascule, retour, test mensuel) est suivie de `select app_cloud_after_restore();` (migration 0011) : comptes Cloud en pause « restored », toutes les sessions effacées, fenêtres et tâches Cloud annulées, coupe-circuit levé. **Conséquences** : après une restauration, chaque client se reconnecte et reprend lui-même ; une session supprimée reste dans les sauvegardes, chiffrée, jusqu'à 30 jours (dit dans le texte d'accord), sans jamais être réutilisée ; durées réelles à mesurer sur la machine.

## D32 — Selio Radar : lecture en direct depuis le compte Achat, par Selio Cloud (29 octobre 2026)

## D33 — Selio Radar : ralentissement automatique au-delà de 1 blocage pour 1 000 pages, seule réaction (29 octobre 2026)
**Contexte** : la seule réaction permise à un signal de Vinted est de ralentir ; une revue a montré qu'un facteur porté par la recherche bloquée laissait les autres recherches du même compte à 60 s et se remettait à ×1 en recréant la recherche, et que les blocages pendant un achat n'étaient pas comptés. **Décision** : chaque lecture et chaque achat écrivent une mesure `radar_reads` (pages, résultat) ; fenêtre glissante des 1 000 dernières mesures en direct de l'organisation ; au-delà de 1 blocage pour 1 000 pages, le facteur **de l'organisation** double (60 → 120 → 240 s…, plafond ×64), pour toutes ses recherches en direct, et il est divisé par deux par tranche de 24 h sans blocage ; il est gardé hors des recherches (`radar_org_state`). Les pages d'un achat comptent dans les plafonds de pages par minute (organisation et machine). Trois lectures anormales de suite (page non reconnue, 5xx, délai) arrêtent la lecture de la recherche (réactivation par le client) et doublent le facteur. La mesure d'une lecture est écrite avant le traitement des annonces ; les lectures sont datées de l'heure prévue du passage (rythme de 60 s et 30 s tenu avec plusieurs recherches). **Conséquences** : un blocage ralentit tout le compte Achat et l'organisation ; aucune autre réaction automatique (ni changement d'adresse, ni de compte, ni d'empreinte) ; taux réel à mesurer.

## D34 — Selio Radar : revente estimée par les ventes proches (modèle 2), avec repli par marque et catégorie (29 octobre 2026)

## D36 — Radar Auto : deux verrous, réservé à l'équipe sur l'adresse partagée, porte-monnaie Vinted, 3-D Secure attendue du client (29 octobre 2026)

## D37 — Selio Radar : prix d'achat reporté dans Manager, « Je l'ai achetée » jamais bloqué (29 octobre 2026)
